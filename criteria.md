# Writing criteria for this guide

Every "for Mere Mortals" guide is written to the same nine-point
standard, so a reader who trusts one can trust the rest. Here it
is, with the verification notes for this particular guide below.

1. **Fix it first.** Reader outcomes lead, not action items: each
   chapter opens by naming the outcome it delivers, shows a check
   the reader can run to confirm they got it, and a reasonable
   reader finishes able to state what was done, what it means,
   and what to try next.
2. **Plain language.** Short sentences, everyday vocabulary,
   technical terms defined on first use. No slang, and no
   idioms that only make sense in one country — the reader may
   be translating as they go.
3. **No dead ends.** A guide never tells the reader to do
   something it cannot show them how to verify. Every claim a
   reader relies on — an install, a command, an output — is
   something this guide demonstrates or clearly labels
   documented-only below.
4. **Live-verified where it matters.** Procedures are run for
   real in the guide's lab wherever the build machine allows it,
   and the transcripts kept in the repository are the evidence.
   What could not be run is listed honestly below, never
   presented as if it had been.
5. **General audiences.** Nothing in this guide — examples,
   fixtures, names, addresses — is modelled on any particular
   reader or author's real life, network, or organisations.
   The lab's server, accounts and files are invented for the
   lab and are stock material throughout.
6. **Standalone.** A reader needs this guide, its lab, and
   nothing else. Where another guide would genuinely help, it
   is pointed to once, by name, and the chapter still completes
   without it.
7. **Honest about limits.** The limits chapter names what the
   tool cannot do: it cannot invent data past the PAR2
   arithmetic, cannot beat a server's retention, does not find
   content, is not a newsreader, depends on external par2 and
   unrar programs, trusts its NZB inputs, and verifies bytes —
   never what the content is or whether it should have been
   fetched.
8. **The ethics rule is in the text, early.** A downloader
   raises the question other guides in this series do not:
   chapter 1 and the README draw the line before any procedure
   does — SABnzbd fetches what it is pointed at, the pointing
   is the reader's responsibility, and the guide's examples
   stay with a self-made test file and freely available
   material. No chapter teaches finding or sourcing content.
9. **Builds clean.** The site builds with MkDocs in strict mode
   with no warnings, and a fresh reader following the chapters
   in order reaches the stated outcome of each.

## Verification notes for this guide

The build machine is a shared Ubuntu 24.04 sandbox (Python
3.12.3). SABnzbd **5.1.3** was installed from the official
source tarball `SABnzbd-5.1.3-src.tar.gz` (project GitHub
releases) into a virtual environment from its pinned
`requirements.txt` — `pip install sabnzbd` was tried first and
fails, because the project is not on PyPI; the guide says so.
It ran unmodified, on loopback (`127.0.0.1:8080`), with its
config in a throwaway directory.

The lab had **no real Usenet account**, so it built its own
news server: `sabnzbd-lab/fake-nntp-server.py`, a small NNTP
server answering on `127.0.0.1:1199` (greeting, AUTHINFO,
CAPABILITIES, GROUP, BODY, HEAD, STAT, QUIT) and logging every
command it received. The test cargo was generated by
`sabnzbd-lab/make-test-nzb.py`: a 120,000-byte file of stock
pangrams (SHA-256 `77393660…a50624ef`), yEnc-encoded into four
30,000-byte segments, plus the NZB mapping them. The server
account (`labuser` / `labpass`) is invented, the message IDs
live under `example.invalid`, and the transcripts print them
because they are worthless anywhere else. All transcripts are
in `sabnzbd-lab/transcripts/` (t00–t14).

Run for real, with transcripts as evidence:

- Versions and the full `--help` (t01); the fixture and its
  checksum (t00).
- First run from an empty config: `GET /` answering 303 to
  `/wizard/`, the wizard's language page (title "SABnzbd
  Quick-Start Wizard") and its server form's field list (t02).
- The wizard completed over HTTP — language POST, then the
  server POST (the lab's fake server, 4 connections, SSL off)
  — ending at "Setup is now complete!"; the server written
  into `sabnzbd.ini` under `[servers]`, and the same server
  read back through `mode=get_config&section=servers` with
  every field matching (t02, t03). The version call answered
  without a key: `{"version":"5.1.3"}`.
- The missing-tools lesson, met for real: a first launch
  without par2/unrar posted warnings (`par2 binary... NOT
  found!`, `unrar binary... NOT found!`, "Essential modules
  are missing, downloading cannot start."). After both were
  supplied (distribution packages, unpacked locally), a
  relaunch showed `{"warnings":[]}`, the interface at HTTP
  200 with title "SABnzbd" (t03).
- A complete download: `mode=addfile` accepted the lab NZB;
  history showed **Completed**, 122,409 bytes fetched for the
  120,000-byte file, stored under `Downloads/complete/`; the
  finished file's SHA-256 equals the original's and `cmp`
  calls them byte-identical (t04, t05). The server's log shows
  the whole conversation — AUTHINFO, then one BODY per
  segment, over parallel connections (t06).
- The deobfuscation rename, observed not theorised: the
  finished file came out named after the job (`labtest.bin`),
  the stage report recording "Deobfuscate renamed 1 file(s)"
  (t05, t14).
- Queue pause and resume: the queue paused via API, a job
  added under the pause sat at Queued with `paused: true`,
  and completed after resume (t07).
- Categories: `documents` created via `mode=set_config`
  (folder `documents`, post-processing 3), read back alongside
  the built-ins (`*`, movies, tv, audio, software, all at
  priority −100 = inherit); a job added with `cat=documents`
  completed into `Downloads/complete/documents/…` (t07).
- Watched folder: `dirscan_dir` set via API; an NZB dropped
  in appeared in the queue as Downloading within the scan
  and completed (t10).
- The connection boundary, genuinely: the fake server was
  killed mid-download; warnings and log show `Failed to
  connect: [Errno 111] Connection refused …@127.0.0.1:1199`;
  when the server returned, both interrupted jobs completed
  without intervention (t08, and history in t13's run).
- **Repair, end to end:** a second fixture
  (`make-repair-nzb.py`) pointed the NZB's fourth segment at
  a message ID the server answers 430 to, and included a real
  PAR2 set (`par2` 0.8.1, 30,000-byte blocks). Attempt 1, with
  one recovery block, failed in history with "Repair failed,
  not enough repair blocks (1 short)" (t12). Attempt 2, with
  two recovery blocks, completed: stage report "1 articles
  were missing … Verified … repair is required; Repaired",
  and the repaired file is byte-identical to the original
  (t11, t13, t14).
- RSS at the config level: a one-item lab feed
  (`sabnzbd-lab/feed.xml`, served locally) registered via
  `mode=set_config&section=rss` and read back with SABnzbd's
  default accept-all filter row attached (t09).
- Shutdown through the API (`mode=shutdown`), twice.

Documented only — described from the project's documentation,
not run, and the text does not claim otherwise:

- **Downloading from a real Usenet provider.** No account was
  available and no outside articles were fetched. Everything
  up to that boundary — the NNTP conversation including
  authentication, article requests, 430 refusals and
  connection failures — was run against the lab's server and
  is transcribed; the boundary itself is exactly there.
- The RSS polling cycle: feeds are fetched on SABnzbd's
  schedule (the lab's log shows the task set for every
  60 minutes) and the API offers no force-fetch (asking
  returned `"not implemented"`, t09). Feed creation, storage
  and readback are verified; a scheduled fetch firing is not.
- Priority *reordering* between live jobs, and per-job pause:
  queue-level pause/resume and priority values in config were
  exercised; on loopback, jobs finish too fast for order to
  be observable.
- The Windows and macOS installers, distribution packages,
  running under a service manager, HTTPS for the interface,
  and access from other machines — the lab bound loopback
  only, deliberately.
- Unpacking real RAR postings: unrar's presence was verified
  and its absence proved blocking, but the lab's cargo was a
  bare file, so no archive was unpacked by SABnzbd here.
  Repair was verified with PAR2 for real; the unpack stage is
  described from the documentation.
- User scripts, the scheduler, speed limits in action, backup
  servers failing over (the Servers stage line is shown from
  real history; a second server was never configured), and
  the neighbour tools of chapter 11 — characterised, not run.

Fixtures are this guide's own and deliberately generic: a
pangram payload, an invented lab server on loopback, stock
category names, and a one-item RSS feed about the test file
itself. No real provider, account, posting or person appears
anywhere in the lab.
